# Task 6b.1 — WS session baseline: capture response_id + added output items

**Phase:** 6b (Incremental WebSocket delta requests) · **Size:** small · **Depends on:** none

## Objective

Give the Goa Codex provider a per-session record of the last full request `input` and the
last response's `response_id` + added output items, so a later task (6b.2/6b.3) can decide
whether to send an incremental delta. This task only **captures and stores** the baseline;
it does **not** change any request bytes.

## Context to load (only these)

- `_shared-context.md` §1 (WS delta precondition), §2 (WS transport, event parser, AssistantMessage), §3 (invariants)
- `internal/agentic/provider/openai_responses/websocket.go`
- `internal/agentic/provider/openai_responses/provider.go` (`handleResponsesCompleted`, `parseResponsesSSE`)
- `internal/agentic/provider/schema/events.go` (`AssistantMessage`), `schema/types.go` (`Usage`)
- Codex ref (read-only): `../codex/codex-rs/core/src/client.rs` — `get_last_response`, `LastResponse`, `prepare_websocket_request`

## Design constraints

- Do **not** change request serialization or the SSE path — pure capture.
- The capture must be **session-scoped**, not global; concurrent sessions must not cross-contaminate.
- The baseline must be an **owned copy** (deep clone) so later agent operations cannot mutate it.
- No secrets in logs: `response_id` is treated as opaque and only ever hashed in diagnostics.

## Steps

1. Extend the `response.completed` parse struct to also read `response.id` and `response.output` (the added items).
2. Add a minimal carrier for the server response id + added items on the assistant-message/result path (e.g. a field on the WS stream result, or a session-scoped struct the provider populates). Keep it off the SSE path.
3. Introduce a small `wsSessionBaseline` type in the `openai_responses` package holding: `LastInput []schema.Message` (owned copy), `ResponseID string`, `AddedItems []schema.Message` (owned copy). Guard with a mutex or keep it on the per-session provider instance.
4. Populate it on each **successful** WS completion. On failure/cancellation, leave the previous baseline untouched.
5. No-op when the flavor is not Codex.

## Tests

- A fake WS server emitting `response.output_item.done`/`response.completed` with a known `id`; assert the baseline captures `response_id` + items.
- Assert the captured slices are deep copies (mutate the source, baseline unchanged).
- Assert a failed/cancelled stream does **not** advance the baseline.
- Assert non-Codex flavor records nothing.

## Verify

```bash
go test ./internal/agentic/provider/openai_responses/... -run 'Baseline|ResponseID|WSCompleted' -count=1 -race
```

## Completion criterion

The provider stores a session-scoped, deep-copied baseline (`response_id` + added output items + last input) on successful WS turns, leaves it untouched on failure, and all new + existing `openai_responses` tests pass with `-race`.
