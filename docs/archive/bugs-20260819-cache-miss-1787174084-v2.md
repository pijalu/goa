# Cache-miss RCA (corrected) — session 1787174084_qqrf2p5v

Status: **verified — 3 real cache busts totaling 352,768 tokens. No
detector defect; no code change required. The prior "not counted as a CM
bust" conclusion was WRONG.**

## Correction

The first RCA (`bugs-20260819-cache-miss-1787174084.md`) scanned only for
near-zero collapses (`cr < prev*0.5`) and so found only the full miss,
concluding the boundary "is not counted as a CM bust". That was incorrect on
two counts:

1. **The misses WERE counted.** The status bar showed `CM:1|2·352,768`. A raw
   emulation of the live detector (`internal/app/stats_tokens.go`: full =
   zero read after establishment; partial = drop beyond the 1024-token
   tolerance) over all 229 token_stats events reproduces it **exactly**:

   | line | prev cache_read | now cache_read | damage | kind |
   |-----:|----------------:|---------------:|-------:|------|
   | 4,756 | 71,424 | 0 | 71,424 | FULL |
   | 6,806 | 111,360 | 69,888 | 41,472 | PARTIAL |
   | 11,724 | 244,480 | 4,608 | 239,872 | PARTIAL |
   | **total** | | | **352,768** | = CM:1\|2 · 352,768 ✓ |

2. **The fresh-context boundary miss IS counted.** `RunFresh` fires
   `EmitContextReset` which re-arms `resetCacheBustBaseline` — but that only
   clears the baseline so the FIRST turn of the NEW (clean) conversation is
   not penalized. The miss at line 4,756 is the **last turn of the PRIOR
   goal** (its content streams commit `c8c2a97`) reporting `prompt_n=70,042`
   with `cache_read=0` — the prior conversation's own cache was already cold
   on that turn, and it is correctly counted against that conversation. This
   is a genuine provider-side cache miss (the 70k-token prompt got zero cache
   reads), not a detector artifact.

## Root cause of the two partial misses

Both partial misses correlate with **large prompt insertions** (the user's
pasted bug/requirement blocks) that shifted the conversation prefix beyond
the provider's cacheable window, recomputing a suffix:

- **line 6,806 (41,472 tokens)**: immediately follows the turn whose content
  appended the "/stats:cache is incomplete" requirement block (multi-KB
  paste). `prompt_n=39,756`.
- **line 11,724 (239,872 tokens)**: immediately follows the
  `/goal:next:reuse` bug-spec paste; the session had grown to `cr=244,480`,
  and the turn ran `prompt_n=128,759` with only 4,608 cached — a near-total
  recompute consistent with a context-window/compaction event dropping most
  of the cached prefix.

These are true cache misses (real token recompute cost), correctly counted.
The detector's two-mode logic (full zero-read + partial drop-beyond-tolerance)
fired as designed.

## What is NOT a defect

- The detector counted all three; the footer `CM:1|2·352,768` matches the
  event log to the token.
- The fresh-context reset correctly avoids penalizing the new conversation's
  cold start (the turn at line 4,839 reads 72,192 — the re-primed cache).
- Sub-agent (companion/team) turns did not pollute the main detector during
  this session (sub-agent cache stats only began flowing to the recorder with
  the /stats:cache rework, commit `9db0c7f`; before that they were invisible
  to both the footer counter and /stats:cache).

## Residual risk (out of scope for this RCA, flagged)

The multi-agent cache-stats instrumentation just added (commit `9db0c7f`)
feeds sub-agent turns into the shared `TurnRecorder`, but the **footer CM
detector** (`handleTokenStats`) still tracks a single main-conversation
baseline. Sub-agent `EventTokenStats` do NOT reach `handleTokenStats` (they
go through the orchestrator's observer → `RecordSubAgentTurn`, a separate
path), so the footer remains main-conversation-scoped — correct. If sub-agent
token stats are ever routed into `handleTokenStats`, each agent's separate
conversation/cache key would need its own baseline or it would false-trigger
as busts. Noted for any future change.
